## 0. TL;DR —— 只读 20 行

1. **权威脚本 = `external_lua_file\<名字>.lua`**。改它 → 退出关卡 → 重进关卡 = 生效（**不用重启编辑器**，一轮约 20 秒）。`.gil` 会被编辑器整份重写，改它无效。
2. **动态创建控件用 `game.InstantiateClientUIControl(prefabIndex, parent)`**，但它**只对「已存为模板」的控件生效**，且父节点必须是**画布根下的子控件**（不是画布根本身）。
3. **`script:EnableUpdate(true)` 不调用 → `OnUpdate` 永不触发**（第一次卡了 4 轮才发现）。
4. **一次性爆发创建**：实测 **0.256 ms/个**。**分帧创建会慢 20 倍以上**（跨帧固定开销），能不用就不用。
5. **控件总数上限**：**31,744 稳定**；**51,664 实测稳定**（200×200 棋盘 + 108×108 参考图）；**61,440 建成即崩**（引擎销毁脚本、无限重建）。
6. **真彩 24 位可行**：`imageColor = Color.FromRGBA(r,g,b,255)` 每控件独立改色。**调色板方案上限 256 色**，不要用。
7. **数据索引必须「整幅行主序」**：像素 `(x,y)` 在数据里的位置 = `y * PW + x`。**这是整个项目最大的坑**（见 §7）。
8. **每个控件只写一次颜色**。先建后「重绘改色」会产生条纹（引擎对同一控件的二次改色有采样痕迹）。
9. **空洞/占位不要用数字标记 + `if d then`**：`HOLE_TAG = 16` 不是 `nil`，`if d then` 会把它当有效块 → 整幅图错位一格（见 §7.4）。
10. **取色要用「块自身的格位置」，不是「目标格位置」**（见 §7.5）。
11. **移动后必须重画「源格」和「目标格」两格**，否则源格残留旧图（见 §7.6）。
12. **`showCursor = true`**（在 `ClientUIContainerControl` 上）→ 鼠标出现且光标事件可用。
13. **`disableKeyEventPassthrough = true`**（同上）→ WASD 不再传给 3D 角色 = **固定角色**。
14. **引擎 UI 坐标 y 向下**，`SetAnchoredPosition` 以父控件中心为原点；而「列表行号」y 也向下 —— 但**「向上移动」对应行号减小**，方向映射很容易写反（见 §8.3）。
15. **画布→物理缩放 `s ≈ 1.07 ~ 1.14`（非整数）** → 每个逻辑像素覆盖非整数物理像素 → 存在摩尔纹上限（见 §6.4）。
16. **脚本必须可重入**：引擎会在传送/容器显隐时整棵销毁重建客户端控件，`OnStart` 会跑很多次。
17. **所有存疑 API 都套 `pcall`**；字段名写错是静默失败。
18. **局部变量「先用后声明」会拿到全局 nil** —— 用 `luacheck.js` 静态检查（见 §10.3）。
19. **诊断优先**：先写「探针脚本」把真实数据打进日志，再动手改代码。靠截图/猜猜了 10 轮，靠日志 1 轮定位。
20. **不要在 `.gil` 里塞任何东西**（除了 `external_lua_file`）。

- 试玩时游戏进程是**原神本体**（`YuanShen.exe`），不是编辑器进程

### 1.2 文件位置

```
%USERPROFILE%\AppData\LocalLow\miHoYo\原神\BeyondLocal\<UID>\
  Beyond_Local_Save_Level\<关卡ID>\
```

### 1.3 `.gil` 格式

- **无加密**：`[20 字节头] + [明文 protobuf] + [4 字节尾]`
- 头部 = 5 个大端 uint32：`head[0] = 总长-4`、`head[4] = 总长-24`
- **对齐必须用可验证签名**（`u32@0 == total-4` 且 `u32@(N-4) == total-4-N`），**不要猜偏移**（猜错过一次把文件写坏）

关键字段路径：

| 路径 | 含义 |
|---|---|
| `#1` / `#2` | 关卡 ID / 名称 |
| `#9.501` | 根控件组 ID 列表 |
| `#9.502[i]` | 第 i 个界面控件组 |
| `#9.502[i].501` | 控件组 ID（= 运行时的 `prefabIndex`） |
| `#9.502[i].504` | 父级/模板 ID（无 504 = 根组） |
| `#9.502[容器].505[3].503.73.501` | 客户端控件容器的「画布根控件组 ID」 |
| `#50.1.1/.2/.3/.5` | 脚本映射 ID / 脚本名 / **文件名** / Lua 源码 |

### 1.4 唯一迭代通道

```powershell
Copy-Item 新脚本.lua "…\Beyond_Local_Save_Level\<关卡ID>\external_lua_file\<脚本名>.lua" -Force
# 然后：退出关卡 → 重新进入关卡（无需重启编辑器）
```

- **文件名必须与 `#50.1.3` 完全一致**，否则编辑器报「引用丢失 xxx.lua」
- 一轮迭代 ≈ 20 秒 → **一次把诊断信息打全**，不要「改一次日志再跑一次」
- 部署后**校验哈希**：`Get-FileHash 源, 部署`（防止写到一半被编辑器覆盖）

## 2. 客户端控件体系

| 概念 | 是什么 |
|---|---|
| **界面控件组库** | `#9.502`，一堆控件组（一个组 = 一棵控件树） |
| **客户端控件模板** | 「存为模板」的客户端控件 —— **只有它能被动态实例化** |
| **客户端控件容器** | **服务器控件**，把客户端控件显示到主屏。有 `showCursor` / `disableKeyEventPassthrough` |
| **容器画布** | 客户端控件真正被摆放的地方 |

### 2.1 建立顺序（用户手工操作，必须给逐级路径）

```
界面控件组管理 → 界面布局 → 布局详情/自定义 → 点「客户端控件容器」
  → 右侧「画布设置」→【前往编辑】
  → 左下角【添加控件】→ 选「图片」/「文本框」/「光标检测区域」
  → 更快的办法：选中已有控件 Ctrl+C / Ctrl+V
```

**层级结构（本关实测）**：

```
[1073741844] ClientUIPrototypeHierarchyRoot   ← 模板层级根
  └─ 1073741931  已存为模板的图片控件          ← ★ 动态实例化的模板
[画布根] ClientUIContainerControl             ← 容器引用的那个
  └─ [子控件] 图片 / 文本框 / 光标检测区域      ← 脚本挂在这里（不是画布根！）
```

### 2.2 「存为模板」是动态实例化的唯一前提 【实测】

- 用户在画布上建一个「图片」控件 → 右键/底部按钮 **「存为模板」**
- 之后 `game.InstantiateClientUIControl(<模板ID>, <画布根的子控件>)` 才能成功
- **画布上普通摆放的控件不能实例化**（返回 `nil`）
- **模板被删除后 ID 会变**，脚本需要**自动探测**（见 §5.2）

### 2.3 容器开关（`ClientUIContainerControl` 上）

| 字段 | 作用 |
|---|---|
| `showCursor` | **=`true` 后鼠标出现，且所有 CursorEvent 才可用** |
| `disableKeyEventPassthrough` | **=`true` 后 WASD 不再传给 3D 角色（固定角色）** |

```lua
-- 沿父链找到容器
local node, depth, container = host, 0, nil
while node and depth < 12 do
    if string.find(tostring(node), "ClientUIContainerControl", 1, true) then
        container = node; break
    end
    local ok, p = pcall(function() return node.parent end)
    if ok and p and p.alive then node = p else break end
    depth = depth + 1
end
if container then
    pcall(function() container.showCursor = true end)
    pcall(function() container.disableKeyEventPassthrough = true end)
end
```

**时机**：`disableKeyEventPassthrough` 建议在游戏开始时打开、退出时恢复（否则玩家一进关卡角色就不能动）。

**⚠️ 所有「全局副作用」必须放在「宿主去重检查」之后**（前作 §7.6：放错位置会导致两个脚本实例都改容器、退出时清不干净）。

## 3. 生命周期与可重入

| 回调 | 实测时机 |
|---|---|
| `OnInit` | 脚本实例创建 |
| `OnEnable` | 控件被启用（**关卡开始时一次**） |
| `OnStart` | 紧接着 OnEnable |
| `OnUpdate(dt)` | **需要 `script:EnableUpdate(true)`** |
| `OnDisable` / `OnDestroy` | 控件停用/销毁 |

### 3.1 `script:EnableUpdate(true)` 是必须的 【实测】

```lua
-- 不调用这一行，OnUpdate 永远不会被触发
pcall(function() script:EnableUpdate(true) end)
```

**探针证据**：调用了之后日志出现 `① OnUpdate 被调用第 1 次 / 60 次 / 780 次`，一直稳定 30fps。

> **血泪**：我因为这个漏掉一行，连续 4 轮误判成「分帧创建被引擎销毁」，实际是「在等一个永不来的回调」。

### 3.2 引擎会销毁重建客户端控件 → 脚本必须可重入 【实测】

- **触发时机**：传送、切换带传送功能的选项卡、容器「隐藏→显示」
- 重建后 `OnInit → OnEnable → OnStart` 重跑，`setupGame()` 会被调用很多次
- 所以：
  - 空闲栈/状态要重置
  - 监听注册要一次性开关
  - **动态创建控件前先清掉上一轮创建的**（否则控件无限累积 → 撞上限崩溃）

## 4. 动态创建控件（本项目的核心能力）

### 4.1 `InstantiateClientUIControl(prefabIndex, parent)` 实测可用

前作结论「258 次组合全返回 nil」的原因是：**没试「存为模板」的控件**。
本文实测：**模板 + 画布根的子控件 → 成功**。

```lua
local ctl = game.InstantiateClientUIControl(TEMPLATE, host)   -- host = 画布根的子控件
if ctl == nil then return nil end
ctl:SetAnchorMin(0.5, 0.5)
ctl:SetAnchorMax(0.5, 0.5)
ctl:SetPivot(0.5, 0.5)
ctl:SetSizeDelta(size, size)
ctl.SetImage(ctl, Enum.ImageSource.StaticReference, 100001)   -- 内置直角白图
ctl.imageType = Enum.ImageType.Stretch
ctl.imageColor = Color.FromRGBA(r, g, b, 255)                 -- ★ 每控件独立真彩
```

**要点**：
- **宿主必须是「画布根下的子控件」** —— 挂在画布根本身 → 全部返回 `nil`（踩过）
- 内置图片资源：`100001`（直角白图）、`106011`（圆角白图）
- `imageColor` 是 24 位真彩，**每控件独立**，可做像素画

### 4.2 性能实测（关键数据）

| 项目 | 实测值 |
|---|---|
| **一次性爆发创建** | **0.256 ms/个** |
| 8,192 个（一次性） | 2.10 s |
| 16,384 个（一次性） | 5.9 s |
| **分帧创建（每帧 N 个）** | **>5 ms/个（慢 20 倍以上）** |
| 单控件改一次 `imageColor` | ~0.004 ms |
| 单格重画（1024 个像素） | ~7 ms |
| 全盘重画 16,384 次改色 | 0.09 ~ 0.11 s |

**结论**：**用一次性爆发，不要分帧。** 代价是进关卡时卡几秒，但只卡一次。

```lua
-- 估算公式
build_seconds ≈ total_controls * 0.000256
--补丁：预留 1.5 倍余量应对设备差异
```

### 4.3 控件总数上限 【实测】

| 控件数 | 结果 |
|---|---|
| 16,384 | ✅ 稳定 |
| 31,744 | ✅ 稳定（能玩） |
| 37,264 | ✅ 稳定（160×160 棋盘 + 108×108 参考图） |
| **51,664** | ✅ **稳定（200×200 棋盘 + 108×108 参考图 —— 实测最高可用配置）** |
| 61,440 | ❌ **建成后引擎销毁脚本 → 无限重建循环**（30 秒建完、立刻崩） |
| 77,824 | ❌ 未测到底（预计更早崩） |

**上限区间：51,664 ~ 61,440**（实测 51,664 稳定、61,440 崩）。
**安全做法**：控制在 **52,000 以内**；超过就降分辨率或去掉参考图。

> **崩溃的表现值得记住**：日志显示「构建完成：61440 个控件（失败 0）」，然后**立刻** `OnDestroy` + 重新 `OnStart`，无限循环。画面卡死、重启游戏也无效（因为脚本一进关卡就重建）——止血方法是**把脚本换成空脚本**（改 `external_lua_file` 即可，不用碰 `.gil`）。

## 5. 模板与画布探测（探针脚本优先）

### 5.1 为什么要先写探针

**10 轮靠截图猜 vs 1 轮靠日志定位** —— 差距就是有没有探针。

### 5.2 模板自动探测（模板 ID 变化时的自适应）

原理：**用不存在的 ID 调 `InstantiateClientUIControl` 只是返回 `nil`，代价很小** → 可以直接扫区间。

```lua
local function discoverTemplate()
    local prio = { 1073741931, 1073758498, 1073741926, 1073758497 }
    for i = 1, #prio do
        local ok, res = pcall(game.InstantiateClientUIControl, prio[i], host)
        if ok and res ~= nil then
            pcall(game.DestroyClientUIControl, res)
            return prio[i], "已知候选"
        end
    end
    local ranges = {
        { 1073741800, 1073742100 },
        { 1073758300, 1073759000 },
    }
    for r = 1, #ranges do
        local a, b = ranges[r][1], ranges[r][2]
        for id = a, b do
            local ok, res = pcall(game.InstantiateClientUIControl, id, host)
            if ok and res ~= nil then
                pcall(game.DestroyClientUIControl, res)
                return id, string.format("扫描 %d..%d", a, b)
            end
        end
    end
    return nil, "全部失败"
end
```

**⚠️ 只判断「能实例化」是不够的**：可能扫到**不是图片控件**的模板（渲染成白方块、忽略 `SetImage`）。
**必须验证类名**：

```lua
local cls = tostring(ctl)     -- 例 "ClientUIImageControl:82"
if string.find(cls, "ClientUIImageControl", 1, true) then ... end
```

### 5.3 运行时控件枚举

- **不要用固定范围 ID 枚举**（ID 全局递增不复用，反复重建会一路涨：`:1` → `:31` → `:61`）
- **正确做法**：`script.object:GetChildren()` 直接枚举画布根的子控件
- 前作的「控件池」方案（`game.GetClientUIControl(id)` 扫 1..80 + `SetVisible` 复用）在**不需要海量控件**时更省性能，可作备选

## 6. 像素渲染：把画布变成一张图

### 6.1 总体架构（本实战验证可行）

```
① 探针      → 确认模板可用 + 拿模板 ID
② 布局      → 算 CELL（每逻辑像素画布单位）、棋盘尺寸、参考图位置
③ 一次性建  → PW*PW 个控件，每个控件 = 一个逻辑像素
④ 一次画到位→ 建控件时就设最终颜色（★ 绝不二次改色）
⑤ 逻辑状态  → cellPiece[g] = 该格放的块；pieceCell[d] = 块在哪格
⑥ 移动      → 只重画「源格」+「目标格」两个格子
```

### 6.2 坐标系统（务必分清）

| 名称 | 含义 |
|---|---|
| **画布单位** | `game.GetUICanvasSize()` 返回，实测 `1599 × 899`（非整数时取整） |
| **逻辑像素边长 `CELL`** | 每个控件占多少画布单位 |
| **棋盘尺寸** | `PW * CELL`（PW = 逻辑像素边长，如 160） |
| `BOARD_X/Y` | 棋盘中心（`SetAnchoredPosition` 以父控件中心为原点） |

```lua
-- 正确的画布→屏幕映射（控件坐标）
local half = (PW - 1) * 0.5
ctl:SetAnchoredPosition(BOARD_X + (px - 1 - half) * CELL,
                        (half - (py - 1)) * CELL)      -- ★ y 用 (half - …)，因为屏幕 y 向下
```

### 6.3 数据索引 ★★★ 本项目最大的坑

**数据必须是「整幅 PW×PW 行主序」**：

```
数据索引（1-based）= y * PW + x + 1        （x, y 为整图坐标，0-based）
```

**块 d（0-based）的格内像素 (bx, by) 在整图中的位置**：

```
gy = 块 d 的格行（0..3）        gx = 块 d 的格列（0..3）
全局 y = gy * K + by           全局 x = gx * K + bx     （K = PW / 4）
数据索引 = (gy * K + by) * PW + (gx * K + bx) + 1
```

**❌ 错误写法（我写了十几轮）**：

```lua
-- 把块 d 当成数据里的连续段 [d*K*K, (d+1)*K*K)
col = tpix[(d - 1) * K * K + by * K + bx + 1]
```

**为什么错**：`by` 方向的步长用了 `K`（32），而整幅图的**行宽是 `PW`**（128/160）。
后果：**块内第 2 行起就读到了别的块** → 块内出现**横条**；而 **X 方向恰好正确**（`+bx` 在两种解释下数值相同）
→ 症状是「**只有 Y 方向错**」，非常容易被误判成渲染问题。

**验证方法（强烈建议写进生成器）**：

```python
# 生成后立即自检：每个块内部颜色种类必须为 1（单色块测试）
for d in range(16):
    gr, gc = d // 4, d % 4
    reg = set(px[(gr*K + by)*PW + (gc*K + bx)] for by in range(K) for bx in range(K))
    assert len(reg) == 1, '块 %d 多色，索引约定不一致！' % (d+1)
```

**这条自检如果早写，能省 10 轮往返。**

### 6.4 画布→物理缩放与摩尔纹上限

- 实测 `s ≈ 1.07 ~ 1.14`（1 画布单位 ≈ 1.1 物理像素），**非整数**
- 所以**每个逻辑像素覆盖非整数物理像素** → 必然存在混叠
- **精度误差** `ε = frac(CELL × s)`，`ε = 0.5` 时最差（每格都跨两个物理像素）
- 经验：
  - 每个逻辑像素 **≥ 6 物理点**时观感可接受
  - 内容相邻像素**色差小**（缩略图）时，混叠被内容吸收 → 看着干净
  - 内容相邻像素**色差大**（打乱的马赛克）时，混叠暴露 → 看着有噪点/条纹
- **不要指望靠「调间距」消除**：修正量被量化到整数画布单位，`s` 的分母又很大（周期几百格），数学上闭合不了
- **要真正像素完美**，只有两条路：① 改画布分辨率使 `s` 为整数；② 一个控件承载一整块图（需要传资源）

### 6.5 「一次画到位」vs「先建后重绘」★

| 做法 | 结果 |
|---|---|
| 建控件时**直接设最终颜色**（每控件只写一次） | ✅ 干净 |
| 先建 + 之后 `redrawAll` 改一遍颜色 | ❌ **条纹**（引擎对同一控件的二次改色有采样痕迹） |

**所以**：初始状态的颜色必须在 `newBlock` 时算好（把打乱状态直接算进取色索引），**不要事后重绘全盘**。
移动时才对**受影响的 2 个格子**重画（此时必须改色，但只改 2 格共 2×1024 个像素，约 14 ms）。

### 6.6 空洞/占位的正确表示

```lua
-- ❌ 错误：HOLE_TAG = 16 不是 nil，if d then 会把它当有效块
if d then col = tpix[...] else col = HOLE_COLOR end

-- ✅ 正确
if d and d ~= HOLE_TAG then col = tpix[...] else col = HOLE_COLOR end
```

**后果**：空洞格被画成「第 16 块」的内容，而**真正属于该格的那一块永远不显示** → **整幅图错位一格**。

### 6.7 取色必须用「块自身」的位置

```lua
-- ❌ 用目标格的位置取色
col = tpix[(gy * K + by) * PW + (gx * K + bx) + 1]     -- gy/gx 是目标格

-- ✅ 用块自身在整图中的格位置
local dgy, dgx = math.floor((d-1)/4), (d-1)%4
col = tpix[(dgy * K + by) * PW + (dgx * K + bx) + 1]
```

**目标态下两者相同**，所以不打乱时不会暴露；**打乱后必错**。

### 6.8 移动后必须重画两格

```lua
local function applyMove(d, fromG, toG, dur)
    cellPiece[fromG], cellPiece[toG] = HOLE_TAG, d
    pieceCell[d], pieceCell[HOLE_TAG] = toG, fromG
    paintCell(fromG)      -- ★ 源格：现在变空，涂空洞色
    paintCell(toG)        -- ★ 目标格：现在有块
end
```

只重画目标格 → **源格残留旧图**（看起来像块被复制了一份）。

## 7. 图像数据管线

### 7.1 数据格式（真彩 RLE）

```
每 4 字节一组： [R][G][B][run]      run = 1..255（重复次数）
Lua 里存成 hex 字符串，解包：
```

```lua
local function unpackTruecolor(hex, expect)
    local raw = (hex:gsub('%x%x', function(cc) return string.char(tonumber(cc, 16)) end))
    local out, n, i, len = {}, 0, 1, #raw
    while i + 3 <= len do
        local r, g, b, run = string.byte(raw, i), string.byte(raw, i+1),
                             string.byte(raw, i+2), string.byte(raw, i+3)
        for _ = 1, run do n = n + 1; out[n] = { r, g, b } end
        i = i + 4
    end
    if expect and n ~= expect then
        err(string.format("解包长度 %d != 期望 %d", n, expect))   -- ★ 必须硬校验
    end
    return out
end
```

### 7.2 硬校验（防止「空数据静默通过」）★

```lua
if #bpix ~= PW * PW then
    err(string.format("!! 棋盘数据长度 %d != 期望 %d，终止", #bpix, PW * PW))
    return
end
```

**为什么必须**：我用 `if color then ctl.imageColor = ... end` 的防御式写法，结果**空数据表被静默当成「没有颜色」**，16384 个控件全部保持默认白色 → 屏幕一片白，查了好几轮。

### 7.3 调色板 vs 真彩

- **调色板索引是 1 字节 → 上限 256 色**。96 色会把渐变压成色块。
- **不传资源的唯一高清路线 = 真彩直传**：每控件一个 `Color.FromRGBA(r,g,b,255)`
- 本实战实测颜色数 **12,993 色**（对比 96 色调色板 = +135 倍）

## 9. 华容道玩法逻辑（可复用的拼图骨架）

```lua
N = 4                      -- 4×4
EMPTY_GOAL = 4             -- 空洞的目标格（第一行最右）
HOLE_TAG   = 16            -- 占位编号（不是 nil！）

cellPiece[g] = 该格放的块编号（空洞格 = HOLE_TAG）
pieceCell[d] = 块 d 所在的格

-- 目标态：块 d 在格 d，且 EMPTY_GOAL 与 HOLE_TAG 两格互换
function reset()
    for g = 1, N*N do cellPiece[g] = g; pieceCell[g] = g end
    local a, b = EMPTY_GOAL, HOLE_TAG
    cellPiece[a], cellPiece[b] = b, a
    pieceCell[a], pieceCell[b] = b, a
end

-- 判定：空位必须在 EMPTY_GOAL，且两个例外格互换到位，其余格 g 上是块 g
function isSolved()
    if pieceCell[HOLE_TAG] ~= EMPTY_GOAL then return false end
    if cellPiece[EMPTY_GOAL] ~= HOLE_TAG then return false end
    if cellPiece[HOLE_TAG] ~= EMPTY_GOAL then return false end
    for g = 1, N*N do
        if g ~= EMPTY_GOAL and g ~= HOLE_TAG and cellPiece[g] ~= g then return false end
    end
    return true
end

-- ★ 保证可解：从目标态做反向随机游走
function scramble(steps)
    for _ = 1, steps do
        local e = pieceCell[HOLE_TAG]
        local r, c = rowOf(e), colOf(e)
        local cand = {}
        if r > 1 then cand[#cand+1] = e - N end
        if r < N then cand[#cand+1] = e + N end
        if c > 1 then cand[#cand+1] = e - 1 end
        if c < N then cand[#cand+1] = e + 1 end
        local pick = cand[math.random(#cand)]
        local d = cellPiece[pick]
        cellPiece[e], cellPiece[pick] = d, HOLE_TAG
        pieceCell[d], pieceCell[HOLE_TAG] = e, pick
    end
end

-- 不变量校验（每次移动后都查，能立刻发现逻辑 bug）
local function checkInvariant(tag)
    local n = 0
    for g = 1, N*N do if cellPiece[g] == HOLE_TAG then n = n + 1 end end
    if n ~= 1 then err(string.format("!! 不变量破坏(%s)：空位=%d", tag, n)) end
    return n
end
```

## 11. 排错手册（症状 → 根因）

| 症状 | 根因 | 修法 |
|---|---|---|
| **屏幕一片白** | 数据表为空，`if color then` 静默跳过 → 控件保持默认白 | 解包后**硬校验长度** |
| **块内横条（只有 Y 错）** | 取色索引用 `K` 作行步长，而行宽是 `PW` | 用 `(gy*K+by)*PW + (gx*K+bx)` |
| **整幅错位一格** | `HOLE_TAG` 是数字不是 nil，`if d then` 把它当有效块 | `if d and d ~= HOLE_TAG then` |
| **移动后源格残留** | 只重画了目标格 | 两格都重画 |
| **打乱后颜色错乱** | 取色用了「目标格」位置 | 用「块自身」位置 |
| **先建后重绘 → 条纹** | 同一控件被二次改色 | 一次画到位 |
| **`OnUpdate` 从不触发** | 漏 `script:EnableUpdate(true)` | 补上 |
| **实例化全返回 nil** | ① 模板不是「存为模板」的控件 ② 宿主是画布根本身 | 存为模板 + 宿主用画布根的子控件 |
| **脚本无限重建/卡死** | 控件数超上限（>~4 万） | 降分辨率；止血=换空脚本 |
| **`attempt to index a nil value (global 'x')`** | 局部变量作用域（`local` 在别处） | 提升为模块级变量 |
| **移动完全无反应** | 处理函数内抛错（堆栈会指到行号） | 看报错日志的行号 |
| **点击命中格上下镜像** | `GetUIPos()` 以左下角为原点 | `playCellAt(x - W/2, H/2 - y)` |
| **WASD 让角色乱跑** | 没开 `disableKeyEventPassthrough` | 容器上设 `true` |
| **鼠标不出现 / 光标事件无效** | 没设 `showCursor` | 容器上设 `true` |
| **方向反了** | 行号 y 与屏幕 y 的映射写反 | 实测确认后调整映射表 |
| **退出后界面自己冒出来** | 容器只开没关（前作 §15） | 退出时 `[384] 显示状态=关闭` |

## 13. 复盘：本实战走的弯路（附「本可以怎么省」）

| 弯路 | 根因 | 本可以 |
|---|---|---|
| 4 轮误判「分帧创建被引擎销毁」 | 漏 `script:EnableUpdate(true)` | 第一轮就写探针测 OnUpdate |
| 3 轮怀疑 `SetAsLastSibling` / `pcall` 开销 | 没先做**逐档 API 计时** | 先跑 `perf_probe`（每档 1024 个，8 行日志定位） |
| 5+ 轮调分辨率 / ε / 块分组 | 真凶是**数据索引约定**（`K` vs `PW`） | 生成器 + 渲染器**共享同一索引公式并各自自检** |
| 2 轮「屏幕一片白」 | 空数据被 `if color then` 静默吞掉 | 解包后**硬校验长度** |
| 2 轮「整幅错位」 | `HOLE_TAG` 数字被当有效块 | 空洞判据用 `d ~= HOLE_TAG` |
| 1 轮「移动无反应」 | 处理函数抛错（`bpixReal` 全局 nil） | 动作全套 `pcall` + `printerr` 堆栈 |
| 1 轮「源格残留」 | 只重画目标格 | 移动即重画两格 |
| 2 轮「参考图消失」 | 绘制循环被改成 `if false then` 没恢复 | 每次改动后核对「应存在的绘制段数量」 |
| 多次误判控件数上限 | 把「移动报错」误读成「脚本被销毁」 | **看报错堆栈**，它会明确指到行号 |

**最大单点经验**：
> **先把「数据约定」和「渲染约定」写在同一份文档里（本文 §6.3），并让生成器和渲染器各自自检。**
> 我花在「索引约定不一致」上的往返，超过了其余所有问题的总和。
