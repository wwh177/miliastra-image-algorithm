# 大批量控件创建（> 50,000）· 分帧创建方法

> **适用场景**：图片像素渲染 / 大地图 / 任何需要 **超过 5 万个客户端控件** 的项目。
> **一句话**：把"一次建完"拆成"每帧建一点"，并全程隐藏、建完分帧显示。
>
> 本文全部数字来自 **实测**（2026-10，原神 千星奇域 6.x，客户端控件）。

---

## 0. ★ 先决策：到底该不该用分帧？

**阈值：50,000 个控件。**

| 控件数 | 推荐做法 | 理由 | 实测 |
|---|---|---|---|
| **≤ 10,000** | **OnStart 单次回调** ✓✓ | 总耗时最短、代码最简单、无需状态机 | 5,000 → 1.35 s；10,000 → 2.71 s |
| **10,000 ~ 50,000** | **OnStart 单次回调** ✓（推荐） | 仍然最快；进关卡时一次性建完 | 20,000 → 8.06 s |
| **50,000 左右** | **OnStart 单次回调**（临界） | 约 22 s，**实测安全但已到边缘** | 50,000 → ≈22 s（实测正常 ✓）|
| **> 50,000** | ★ **必须分帧创建** | 单次回调超时 → 被看门狗【静默中断】 | 61,440 → 失败 ✗ |
| > 100,000 | 分帧创建 + 隐藏 + 分帧显示 | 唯一可行路径 | 132,000 → 166 s ✓ |

**为什么"少控件时单次回调更快"** —— 实测同规模对比：

```
20,000 个控件：
   OnStart 单次回调       8.06 s   ✓✓ 更快
   分帧创建（隐藏，40ms/帧） 10.78 s  ✗ 慢 34%

原因：分帧的每一帧都要额外遍历"已存在的全部控件"（隐藏态约 1.7 µs/个·帧），
      控件少时这笔额外开销反而超过了它省下的东西 ✗
```

**所以**：
- **控件少（≤50,000）→ 老老实实 OnStart 一次建完** ✓ 更快也更简单
- **控件多（>50,000）→ 别无选择，必须分帧** ✓

> ⚠️ **但"隐藏 + 分帧显示"是另一回事**：无论控件多少，都建议
> **挂在隐藏组下建立 → 建完分帧显示** ✓（为的是**运行帧率提升约 9 倍**，
> 以及避免"一次显示 10 万个"卡死一帧）。这与"用不用分帧创建"是**两个独立决定**：
>
> | | 创建方式 | 隐藏/显示方式 |
> |---|---|---|
> | ≤50,000 | OnStart 一次建完 ✓ | 仍建议隐藏建立 + 分帧显示 ✓ |
> | >50,000 | 必须分帧创建 ✓ | 必须隐藏建立 + 分帧显示 ✓ |

## 0. 先破除三个旧结论（它们都是错的）

| 旧结论 | 实际情况 |
|---|---|
| ❌ "控件数上限 52,000，超过就崩溃" | **没有硬上限**。实测 **100,000 个控件不崩溃**，167,915 个也能建成 ✓ |
| ❌ "崩溃是因为控件太多" | 崩溃原因是 **单次回调执行太久**（引擎看门狗），与控件总数无关 |
| ❌ "建得慢是 Lua 慢" | Lua 侧可忽略；**瓶颈全在引擎的 Instantiate 与每帧 UI 遍历** |

**看门狗的真实表现**（这是最关键的认知）：

```
日志：Lua execution took too long. Please check for infinite loops.
stack traceback:
    pixel_puzzle:332: in function 'b64decode'
    pixel_puzzle:358: in function 'parseAll'
    pixel_puzzle:525: in function 'OnStart'
```

引擎会给一次回调约 **20 秒**预算，超时后 **中断脚本**（不是报错退出，而是**静默截断**——
实测一次解析 167,915 个块被截断在 **132,000** 个，`#DATA` 只剩 220/280 段，
表现为"图像下方少了一条"，**没有任何显式错误**）。

## 1. 三个实测成本模型

### 1.1 创建控件的成本（含退化项）

```
每控件耗时 ≈ 0.27 + 3.75e-6 × 已有控件数   (ms)
总耗时     T ≈ 0.27·N + 3.75e-6·N²          (ms)
```

| N | 实测每控件 | 实测总耗时 |
|---|---|---|
| 5,000 | 0.270 ms | 1.35 s |
| 10,000 | 0.271 ms | 2.71 s |
| 20,000 | 0.403 ms | 8.06 s |
| 65,440 | 0.724 ms | 37.9 s（跨帧隐藏） |
| 132,000 | 1.258 ms | 166 s（跨帧隐藏） |

**重要**：
- 二次项是**引擎内部的全局性开销**（不是兄弟节点数——实测把 167,915 个控件分到 12 个组、
  每组仅 1.4 万个，退化曲线**完全不变**）
- 加大每帧批量只能改善约 **1.4 倍**（实测），**换不来数量级提升**
- 所以 `T≈0.27N` 是**理论下界**：167,915 个至少要 **45 秒**，不可能更快

### 1.2 每帧渲染/更新成本（决定"能不能玩"）

```
每帧耗时 ≈ 15~18 µs × 【可见】控件数      ← 严格线性（实测三点吻合）
```

| 可见控件数 | 实测帧时间 | 帧率 |
|---|---|---|
| 5,000 | 80.9 ms | 12 fps |
| 10,000 | 150.4 ms | 7 fps |
| 20,000 | 300.8 ms | 3 fps |

**⚠️ 这条才是真正的天花板**：20,000 个可见控件就已经只有 3 fps ✗

### 1.3 ★ 隐藏态的每帧成本（本文的核心杠杆）

| 状态 | 每帧耗时 | 每控件 |
|---|---|---|
| 20,000 个 **可见** | 300.8 ms | **15.0 µs** |
| 20,000 个 **隐藏** | 33.2 ms | **1.7 µs** |
| **20,000 个：隐藏建立 → `SetVisible(true)` 显示** | **35.3 ms** | **1.8 µs** ✓✓ |

**结论：隐藏 → 显示 这个"转换"会触发引擎重建高效渲染批次，帧开销降约 9 倍** ✓✓
（实测：20,000 个从 300 ms 降到 **35 ms**，且画面确认全部正常渲染）

## 2. ★ 分帧创建的标准做法（可直接抄）

> **只有控件数 > 50,000 时才需要这一节**；≤50,000 请直接用 OnStart 一次建完 ✓（更快更简单）

### 2.1 四个要点

```
① 解析/解码数据也要分帧   —— 一次性解析大数据 = 看门狗截断（最隐蔽的坑）
② 建立时全程隐藏          —— 每帧成本 1.7 µs/个，而不是 15 µs/个
③ 建完用 SetVisible(true) —— 这一次"转换"换来约 9 倍帧率
④ 显示也要分帧            —— 否则一次显示 10 万个控件同样会卡死一帧
```

### 2.2 正确的显示/隐藏 API（★ 极易踩坑）

```lua
-- ✗ 错误：点号赋值会失败（且被 pcall 吞掉后毫无提示）
c.visible = false          -- cannot set visible
c.active  = false          -- cannot set active

-- ✓ 正确：必须用冒号调用
c:SetVisible(false)        -- 隐藏
c:SetVisible(true)         -- 显示
c:SetActive(false)         -- 同时停用（更彻底）
c:SetActive(true)
```

> **血的教训**：早期探针用 `ctls[i].visible = false` 包在 pcall 里，
> 调用**静默失败**，却因此得出"隐藏没有收益"的错误结论，
> 一度放弃了整个分帧方案。**测 API 一定要打印 pcall 的返回值。**

### 2.3 分帧显示（多组 + 逐组显示）

一次性 `SetVisible(true)` 让 10 万个控件同时可见时，引擎要在**一帧内**重建全部渲染批次 ✗。
做法：建立时就分成 K 个独立的组，**每帧只显示一组**：

```lua
-- 建立阶段：建 K 个全屏透明组，全部隐藏
groups = {}
for i = 1, K do
    local g = game.InstantiateClientUIControl(A_IMAGE_TEMPLATE, root)
    g:SetAnchorMin(0.5, 0.5); g:SetAnchorMax(0.5, 0.5); g:SetPivot(0.5, 0.5)
    g:SetSizeDelta(canvasW, canvasH); g:SetAnchoredPosition(0, 0)
    g.SetImage(g, Enum.ImageSource.StaticReference, RECT_IMG)   -- 内置纯色图
    g.imageType = Enum.ImageType.Stretch
    g.imageColor = Color.FromRGBA(0, 0, 0, 0)                   -- 全透明
    g:SetVisible(false)
    g:SetActive(false)
    groups[#groups + 1] = g
end

-- 显示阶段：每帧只显示一组（这一帧的"转换"成本被摊到 K 帧）
function OnUpdate(dt)
    if phase == PH_REVEAL then
        local g = groups[reveal_idx]
        if g then g:SetVisible(true); g:SetActive(true) end
        reveal_idx = reveal_idx + 1
        if reveal_idx > #groups then phase = PH_DONE end
    end
end
```

**子控件坐标不受影响**：所有组都居中且同尺寸，子控件用
`anchorMin=anchorMax=(0.5,0.5)` + `SetAnchoredPosition(x, y)`，
位置就是相对**组中心**（= 屏幕中心）→ 与"平铺挂在根下"完全等价 ✓

### 2.4 分帧建立主循环（默认 40 ms/帧）

```lua
local BUDGET = 0.040        -- ★ 每帧预算（秒）。40 ms = 平滑但慢；120 ms = 快但略顿
local PH_IDLE, PH_PARSE, PH_BUILD, PH_REVEAL, PH_DONE = 0, 1, 2, 3, 4
local phase, blocks, bidx, groups, ctls = PH_IDLE, {}, 1, {}, {}

function OnUpdate(dt)
    if phase == PH_PARSE then
        -- ① 解析/解码也分帧：每帧只处理若干段
        local t0 = os.clock()
        local done = 0
        while chunk_idx <= NCH and done < PARSE_PER do
            local raw = b64decode(DATA[chunk_idx])
            -- …逐块解码，append 到 blocks…
            chunk_idx = chunk_idx + 1; done = done + 1
        end
        if chunk_idx > NCH then phase = PH_BUILD; build_t0 = os.clock() end

    elseif phase == PH_BUILD then
        -- ② 建立：每帧不超过 BUDGET 秒；控件挂到【隐藏的组】下
        local t0 = os.clock()
        local n = #blocks
        while bidx <= n do
            local bl = blocks[bidx]
            local c = mkRect(groups[math.floor((bidx - 1) / per_group) + 1],
                             cx(bl), cy(bl), bl[3] * cell + 0.35, bl[4] * cell + 0.35,
                             bl[5], bl[6], bl[7])
            if c then ctls[#ctls + 1] = c end
            bidx = bidx + 1
            if (bidx % 32 == 0) and (os.clock() - t0) >= BUDGET then break end
        end
        if bidx > n then phase = PH_REVEAL; reveal_idx = 1 end

    elseif phase == PH_REVEAL then
        local g = groups[reveal_idx]
        if g then g:SetVisible(true); g:SetActive(true) end
        reveal_idx = reveal_idx + 1
        if reveal_idx > #groups then phase = PH_DONE end
    end
end
```

> **每 32 个检查一次时间**：`os.clock()` 本身也有成本，逐个检查会显著拖慢；
> 32 是个实测好用的粒度（超预算最多多建 31 个）。

### 2.5 解析也要分帧（最容易被忽略）

一次性在 `OnStart` 里解码 16 万个块的实测结果是**被看门狗截断**：

```
现象：图像下方少一条；日志只有一行 "Lua execution took too long" + traceback
根因：parseAll() 在 OnStart 内一次性解码 280 段 × 600 块，远超单次回调预算
修法：解析改为每帧 20 段，共 14 帧完成 ✓
```

**base64 解码器也必须写快**（Lua 里逐字节 `string.char` 是性能杀手）：

```lua
-- ✗ 慢：每字节一次 string.char + 每次算 2^bits（浮点幂）
-- ✓ 快：每 4 字符 → 3 字节，纯整数，一次 string.char（实测快 6~10 倍）
local function b64decode(s)
    local n, out, k, i = #s, {}, 0, 1
    while i + 3 <= n do
        local b1, b2, b3, b4 = string.byte(s, i), string.byte(s, i+1),
                               string.byte(s, i+2), string.byte(s, i+3)
        i = i + 4
        local a, b, c, d = B64[b1], B64[b2], B64[b3], B64[b4]
        if a and b and c and d then
            local v = a * 262144 + b * 4096 + c * 64 + d
            k = k + 1
            -- ★ 先判 b3 再判 b4！（写成先判 b4 会让 "xxx=" 少输出一个字节 → 整段错位）
            if b3 == 61 then      out[k] = string.char(v // 65536 % 256)
            elseif b4 == 61 then  out[k] = string.char(v // 65536 % 256, v // 256 % 256)
            else                  out[k] = string.char(v // 65536 % 256, v // 256 % 256, v % 256)
            end
        end
    end
    return table.concat(out)
end
B64[61] = 0    -- '=' 也要入表，否则整组被跳过
```

> ⚠️ 这段解码器的 `b3`/`b4` 判断顺序踩过坑：先判 `b4` 时 `"xxx="` 会少输出一个字节，
> 表现是**每段末尾错位**（`颜色字节不足`），而且**只在有 padding 的段出现**，极难定位。

## 3. 实测时间表（别人的项目可直接对照）

以 **160,000 个控件**为例：

| 阶段 | 参数 | 实测/预估 |
|---|---|---|
| 解析数据 | 每帧 20 段（共 280 段） | 14 帧，约 3~5 s |
| 隐藏建立 | 40 ms/帧 | 约 **150~220 s**（N² 项主导）|
| 隐藏建立 | 120 ms/帧 | 约 **100~150 s** |
| 隐藏建立 | 2000 ms/帧 | 约 **55 s**（接近下界 45 s）|
| 分帧显示 | 每帧 1 组（12 组） | 12 帧，约 3~5 s |
| **总计** | 40 ms/帧 | **约 2.5~4 分钟**（全程无长冻结 ✓）|

**关键取舍**：
- **每帧预算越大 → 总时间越短，但单帧越顿**
- 实测把预算从 40 ms 提到 120 ms，**总时间只快约 1.4 倍**（不是 3 倍 ✗）
  —— 因为主导项是与预算无关的 `3.75e-6·N²` ✗
- **推荐 40 ms**（用户几乎感觉不到卡顿，只见画面逐步长出）；
  只有在"必须尽快建完"时才提到 200~800 ms

### 实际部署案例（600×600 全屏插画，98,679 个控件）

```
数据：98,679 个矩形，脚本 938 KB（b64 编码 + 分 165 段）
流程：按 P 键 → 解析(9 帧) → 隐藏建立(约 63 s @120ms) → 分帧显示(12 组)
结果：建立完成 63 s，全程最慢帧 ≤300 ms；显示后 69 ms(14 fps) 可交互 ✓
```

## 4. 检查清单（照做即可）

### 4.0 先判断走哪条路

```
控件数 ≤ 50,000  → 用 OnStart 单次回调建立 ✓（更快更简单，本文第 2 节不需要）
控件数 >  50,000  → 用分帧创建 ✓（本文第 2 节全部照做）
无论哪种，都建议：隐藏建立 + 建完分帧显示 ✓（为运行帧率）
```

### 4.1 走分帧路线时逐条确认

- [ ] 数据解析**分帧**（每帧 10~20 段），不放在 `OnStart` 里一次做完
- [ ] base64 解码用"4 字符→3 字节 + 一次 `string.char`"，且 `b3` 先于 `b4` 判断
- [ ] 控件**挂在一个/多个隐藏的组**下（组用透明图片控件：`imageColor` 的 alpha = 0）
- [ ] 隐藏用 **`g:SetVisible(false)` + `g:SetActive(false)`**（不是 `g.visible = false` ✗）
- [ ] 每帧建立量受 **时间预算**控制（默认 40 ms），每 32 个检查一次 `os.clock()`
- [ ] 建完**分帧显示**（每帧显示一组，K=8~16 组）
- [ ] 屏幕上有**进度标签**（已建/总数、本帧耗时、ms/控件、最慢帧）——出问题时这是唯一线索
- [ ] 进度标签挂在**根**下而不是组内（否则隐藏组时标签也看不见 ✗）
- [ ] 提供 **紧急止血**：进关卡前先备份脚本；卡死时用 `tools\kill.bat`
- [ ] 若脚本 > 1.2 MB，注意**引擎对字符串常量的限制**（见下）

### 附：脚本体积与字符串常量

实测一个 **1.58 MB** 的脚本（DATA 表含 280 个 ~4 KB 字符串）曾出现
**只加载到第 220 段**的现象。虽然最终定位到的根因是"解析超时"，
但**建议把单脚本控制在 1.2 MB 以内**更稳妥，做法：

```
① 分帧解析后，数据可以直接用（不必一次性）
② 每个字符串常量控制在 6 KB 以内
③ 若还太大：提高 STD / 用动态 STD / 降低分辨率
```
