## 1. 这个工具解决什么问题

千星奇域的客户端控件**每个只能显示一个纯色矩形**。要显示一张图片，直观做法是
"每个像素一个控件"——但这对 300×300 的图就是 90,000 个控件，**远超引擎上限（约 61,440 会崩溃,50000时能正常跑，50000的量有实操验证过）**。

本工具用**最大对齐矩形合并**把颜色相近的相邻像素合并成大矩形：

| 方案 | 300×300 插画所需控件 | 可行性 |
|---|---|---|
| 逐像素 | 90,000 | ❌ 引擎崩溃 |
| 本工具 STD=3 | ~30,000 | ✓ 稳定 |
| 本工具 STD=8 | ~14,000 | ✓ 稳定，但有可见块状感 |

**关键约束**：合并产生的矩形边界必须落在整数像素坐标上（本工具已保证），
否则相邻矩形之间会出现发丝缝。

### 步骤 1：安装依赖

```bash
pip install pillow numpy
```

### 步骤 2：压缩图片

```bash
# 最简用法：改 compress.py 顶部的 CONFIG 区，然后直接跑
```

   （从 `local IMG = {}` 到 `-- ▲▲▲ 数据区结束 ▲▲▲` 之前）替换成 `out.lua` 的全部内容

### 多档对比工作流（推荐给"调参"场景）

想在同一关卡里**按键切换对比不同 STD**，用这三个脚本一条链：

```bash
# 1) 打包多档（--specs 每档写「分辨率:STD」；默认 b64 编码）
python pack_modes.py --input 图.png --specs 256:1,256:3,200:0 --out modes.lua --preview

# 2) 自动拼进渲染器
python assemble_modes.py modes.lua render_modes.lua 输出.lua

# 3) 把 输出.lua 部署到关卡，进关卡按 P 键切换档位
```

**为什么用字符串编码而不是 Lua 表**（重要经验）：
Lua 表的每个块都是一次"表构造器"。实测：
- 6.2 万个构造器 / 1.23 MB 脚本 → 引擎**正常加载**
- 8.9 万个构造器 / 2.01 MB 脚本 → 引擎**完全无日志**（编译期就失败）

本工具把每档的块列表压成**一个字符串**，所以无论多少块，字符串常量只有"档位数"个，
构造器数量趋近于 0。两种编码可选（坐标 `x,y` **都不存储**，由扫描顺序推演）：

| 编码 | 每块字符 | 说明 |
|---|---|---|
| `hex` | 10 | `w,h,r,g,b` 各 1 字节；可肉眼查看，便于调试 |
| **`b64`（默认）** | **7** | 3 字节 `w,h,r` → 4 字符；2 字节 `g,b` → 3 字符；**比 hex 再省 30%** |

**体积实测（39,853 块）**：旧 Lua 表写法约 143 万字符 → hex 39.9 万 → **b64 27.9 万**
（b64 相对旧写法省 **81%**）。b64 编码与坐标推演**已在真实关卡实测通过**
（hex 与 b64 解码出的块校验和完全一致）。

渲染端解码（`render.lua` / `render_modes.lua` 已实现）：
```lua
-- b64：每块 7 字符，分两组（每步运算 < 2^24，避免 32 位整数回绕）
local base = (i - 1) * 7
local c1,c2,c3,c4,c5,c6,c7 = string.byte(data, base + 1, base + 7)
local a = ((v1*64 + v2)*64 + v3)*64 + v4          -- 24 位 = w,h,r
local w = math.floor(a / 65536)
local h = math.floor(a / 256) % 256
local r = a % 256
local b2 = (v5*64 + v6)*64 + v7                     -- 16 位 = g,b
local g = math.floor(b2 / 256)
local b = b2 % 256
-- x,y 由扫描推演还原（occuped[col] + 游标重放扫描）
```
> ★ **不要在 Lua 里把 5 字节合成 40 位大整数** —— 那需要 42 位中间值，
> 在 32 位整数实现下会回绕（实测：`807136431*64+24` 得到 `117124056` 而非 `51656731608`）。

### 自测怎么跑

```bash
python verify_toolkit.py    # 端到端（推荐先跑这个）
python verify_modes2.py     # 多档链路
python selftest.py          # 基础
```

`verify_toolkit.py` 的关键设计：它**从 render.lua 里抽取实际解码代码**来解压 b64/hex 数据，
并与 Python 端算出的校验和比对 —— 所以测的就是真正会运行的代码，而不是复制品。

期望输出结尾是 `✓ 全部通过`。

> ⚠️ 最后一项非常关键：曾经因为生成的数据表有括号错误，脚本在**编译期**就失败，
> 表现为"进关卡后无日志、无画面"，而只查括号配对的静态检查**发现不了**。
> 所以改完 `compress.py` 或 `render.lua` 后一定要跑 `selftest.py`。

## 4. 参数配置详解

### 4.1 `compress.py` 的参数

两种配置方式，**优先级：命令行 > JSON > 文件内 CONFIG**。

#### 方式 A：改文件内的 CONFIG 区（最简单）

打开 `compress.py`，找到顶部：

```python
CONFIG = {
    "STD": 3,                  # 容差 ← 最重要（动态 STD 会据此自动配好另外六个参数）
    "OUT_W": 300,              # 输出宽（源像素）
    "OUT_H": 300,              # 输出高（源像素）
    "LOCK_ASPECT": False,      # True=锁定长宽比，False=允许变形
    "COLOR_BITS": 8,           # 每通道位数，8=不量化（推荐）
    "INPUT": "input.png",      # 输入图片
    "OUTPUT": "output.lua",    # 输出 lua
    "PREVIEW": False,          # 是否输出重建预览图
    "ENC": "b64",              # 块数据编码：b64（最省，7 字符/块）| hex（10 字符/块）
    "MAX_BLOCKS": 45000,       # 块数告警阈值（单次回调安全值；更多请用分帧创建）
    "VAR_NAME": "IMG",         # 输出 Lua 变量名

    # ---- 动态 STD（★ 默认开启，块数可减 30~34%，见 4.3）----
    "DYN_STD": True,           # 总开关；False = 退回全局 STD（与旧版一致）
    "T1_STD": None,            # 细节区容差；None = 自动 = STD
    "T2_STD": None,            # 过渡区容差；None = 自动 = 2×STD
    "FLAT_STD": None,          # 平坦区容差；None = 自动 = 3×STD
    "T1": 30.0,                # 细节判定阈值（梯度 > T1 → 细节区）
    "T2": 12.0,                # 过渡判定阈值
    "FLAT": None,              # 平坦区上界；None = 自动 = T2
    "DYN_M2": 2.0, "DYN_M3": 3.0,   # 自动时的倍数
    "DYN_R": 2,                # 容差图平滑半径
}
```

#### 方式 B：命令行

```bash
python compress.py \
  --input 图片.png \
  --output 结果.lua \
  --std 3 \
  --size 300x300 \
  --lock-aspect \
  --bits 8 \
  --preview \
  --max-blocks 34000
```

#### 方式 C：JSON 配置文件

```bash
python compress.py --config my_config.json
```

```json
{
  "INPUT": "图片.png",
  "OUTPUT": "结果.lua",
  "STD": 3,
  "OUT_W": 300,
  "OUT_H": 300,
  "LOCK_ASPECT": true,
  "COLOR_BITS": 8
}
```

#### 参数逐个说明

| 参数 | 含义 | 可选值 | 建议 |
|---|---|---|---|
| **`STD`** | **容差**。区域内三通道标准差 ≤ STD 才允许合并。**动态 STD 会据此自动配好另外六个参数** | **0 ~ 1024 任意值**（不再限档位） | **起手用 3**。0 = 无损；越大越省控件、画质越差 |
| **`DYN_STD`** | **动态 STD 总开关（默认 True）** | True / False | **保持 True**（块数少 30~34%）。用 `--no-dyn-std` 可退回旧行为 |
| `T1_STD` / `T2_STD` / `FLAT_STD` | 细节 / 过渡 / 平坦区的容差 | 任意正数 | 默认自动 = STD / 2×STD / 3×STD |
| `T1` / `T2` / `FLAT` | 三个梯度阈值（分区用） | 任意正数 | 默认 30 / 12 / =T2，**不懂别改** |
| `DYN_M2` / `DYN_M3` / `DYN_R` | 自动时的倍数与平滑半径 | 正数 / 整数 | 默认 2 / 3 / 2 |
| `OUT_W` / `OUT_H` | 输出分辨率（源像素数） | 任意正整数 | 常用 200 / 300 / 400 |
| `LOCK_ASPECT` | `True`=按原图比例缩放后居中放入框内（**不拉伸**，空白填白）；`False`=直接拉伸到 OUT_W×OUT_H（**允许变形**） | `true` / `false` | 需要保持比例用 `true` |
| `COLOR_BITS` | 每通道位数，8 = 不量化 | 1~8 | **保持 8**。见下方⚠️ |
| `INPUT` | 输入图片路径 | 任意 Pillow 支持的格式 | png / jpg / webp 都行 |
| `OUTPUT` | 输出 lua 路径 | 任意 | 目录会自动创建 |
| `PREVIEW` | 是否额外输出重建预览图 | `true`/`false` | 调参时开 |
| `MAX_BLOCKS` | 块数超过此值只告警不阻断 | 整数 | 用 45000 |
| **`ENC`** | **块数据编码**：`b64` = 7 字符/块（最省）；`hex` = 10 字符/块（可肉眼查看） | `b64` / `hex` | **保持 `b64`**（比 hex 省 30%） |
| `VAR_NAME` | 输出 Lua 变量名 | 合法 Lua 标识符 | 默认 `IMG` |
| `WITH_RETURN` | 是否在输出末尾加 `return IMG` | `true`/`false` | **保持 `false`** |

> ⚠️ **关于 `WITH_RETURN`（很容易踩的坑）**
> 输出文件默认**不含** `return`。因为你要把它**整段粘进 render.lua 的数据区**，
> 而 Lua 规定 `return` 必须是**块的最后一条语句** —— 粘在中间会直接编译失败，报
> `'<eof>' expected near 'local'`，表现为进关卡后**无日志、无画面**。
> 只有把输出当独立 Lua 模块（`require` / `dofile`）用时才加 `--with-return`。

> ⚠️ **关于 `COLOR_BITS`**：实测结论是**降位数不会减少控件数，反而增加误差**。
> 原因：合并判据是"标准差 ≤ STD"，而插画的平滑渐变本来就在容差内；
> 量化把渐变变成硬边色块后，反而**阻碍**了跨色块边界的合并。
> **所以除非有特殊需求，始终用 `COLOR_BITS = 8`。**

### 4.2 STD 怎么选（画质 vs 控件数）

> **注：下表是"全局 STD"（`--no-dyn-std`）的数据，用于理解 STD 的语义。**
> **动态 STD（默认开启）在同样观感下块数会少 30~34%，见 4.3。**

实测数据（仓库自带样图 `examples/sample.jpg`，300×300，**全局 STD**（`--no-dyn-std`）；
MAE = 相对真彩原图的每通道平均绝对误差，范围 0~255）：

> 以上数值由 V1.1 复测（Python 3.13 / numpy 2.5 / Pillow 12.3）。V1.0 文档里的 STD=3 曾写 30,600 / 1.17，
> 与同一文档 4.3 节的 31,871 自相矛盾，已按实测统一为 **31,871 / 1.07**。

| STD | 块数（约） | MAE | 主观观感 |
|---|---|---|---|
| 1 | 52,500 | 0.30 | 几乎完美，但**控件数超标** |
| 2 | 38,500 | 0.72 | 极佳，**略超安全线** |
| **3** | **31,871** | **1.07** | **✓ 推荐：几乎看不出** |
| 4 | 25,600 | 1.63 | ✓ 轻微 |
| 6 | 18,800 | 2.59 | 轻微块状 |
| 8 | 14,500 | 3.59 | 明显块状 |
| 12+ | < 10,000 | > 5 | 明显失真，仅在控件预算极紧时用 |

**经验判据**：
- **MAE ≤ 1.5** → 一般人看不出
- **MAE ≥ 3.5** → 明显可见

> 注意：**MAE 主要由 STD 决定，与图片内容关系不大**（因为判据本身就是误差阈值）。
> 但**块数**与内容关系很大：平涂/复古风的图块数会显著更少（见下）。

### 4.3 ★ 动态 STD（**默认开启**）

**一句话**：细节区用最严的容差、平坦区用更松的容差 —— **观感不变，块数少三成**。

#### 为什么有效

全局 STD 对整幅图一视同仁：平坦区（通常占 60~70%）用严格容差是**纯浪费**，
而观众真正看的细节区又得不到额外照顾。动态 STD 把预算挪到该花的地方。

#### 实测收益（300×300 插画）

| 用户选的 STD | 动态 STD 块数 | 全局 STD 块数 | **块数减少** | 细节区 MAE 对比 |
|---|---|---|---|---|
| 1 | 37,188 | 53,204 | **−30.1%** | 0.050 vs 0.053 ✓ 持平 |
| 2 | 26,495 | 39,639 | **−33.2%** | 0.218 vs 0.230 ✓ 持平 |
| 3 | 21,141 | 31,871 | **−33.7%** | 0.473 vs 0.501 ✓ 持平 |

**细节区（梯度最强、观众最关注的部分）画质完全持平甚至略好**，
省下来的全是平坦区的冗余 ✓

#### 参数自动推导规则

```
用户只给一个 STD，其余六个参数自动推出：

    t1_std   = STD          细节区容差
    t2_std   = 2 × STD      过渡区容差
    flat_std = 3 × STD      平坦区容差
    t1       = 30           梯度阈值：> t1 → 细节区
    t2       = 12           梯度阈值：> t2 → 过渡区
    flat     = t2           梯度阈值：≤ flat → 平坦区

例：用户选 STD=3 → 三档容差 3 / 6 / 9
```

#### 六个参数的手动接口（任何一项可单独覆盖）

| 参数 | CLI | JSON 键 | 默认 |
|---|---|---|---|
| 细节区容差 | `--t1-std` | `T1_STD` | `STD` |
| 过渡区容差 | `--t2-std` | `T2_STD` | `2×STD` |
| 平坦区容差 | `--flat-std` | `FLAT_STD` | `3×STD` |
| 细节阈值 | `--t1` | `T1` | 30 |
| 过渡阈值 | `--t2` | `T2` | 12 |
| 平坦上界 | `--flat` | `FLAT` | `T2` |
| 倍数（自动时） | `--dyn-m2` / `--dyn-m3` | `DYN_M2` / `DYN_M3` | 2 / 3 |
| 容差图平滑半径 | `--dyn-r` | `DYN_R` | 2 |

#### 关闭动态 STD

```bash
python compress.py --input a.png --std 3 --no-dyn-std    # 退回全局 STD（与旧版完全一致）
```
JSON：`{"DYN_STD": false}`；代码：`CONFIG["DYN_STD"] = False`

> `STD=0`（无损）时会自动关闭动态 STD（无意义）。

#### 关键实现细节（改代码时注意）

1. **分级用的是"区域级"梯度**：对水平/垂直差分的较大者做半径 `r` 的方框平滑，
   否则孤立的高梯度像素会把细节区切得很碎。
2. ★ **矩形生长时必须取「覆盖区内最小容差」**：
   否则从平坦区长出的大矩形会**吃掉细节**。
   实测（300×300）：取最小 → 细节 MAE **0.050**；只取锚点 → **0.094**（差 1.9 倍）。
3. 输出仍然是**扫描顺序块列表**，所以 x,y 依旧可以省略，
   `check_scan_order` 自检照常通过 ✓

## 5. 输入与输出格式

### 5.1 输入

任意 Pillow 支持的图片（`.png` / `.jpg` / `.webp` / `.bmp` …）。

- 若 `LOCK_ASPECT=false`：直接拉伸到 `OUT_W×OUT_H`
- 若 `LOCK_ASPECT=true`：按比例缩放后居中放入 `OUT_W×OUT_H` 的白底画布

### 5.2 输出（Lua 数据表）

```lua
-- 由 compress.py 生成（最大对齐矩形合并压缩）
-- STD=3.0  COLOR_BITS=8  分辨率=300x300  编码=b64  块数=30612  MAE=1.17
-- 用法：把本文件【全部内容】替换进 render.lua 的『数据区』
local IMG = {}
IMG.N = 300            -- 边长（源像素，正方形）
IMG.W = 300            -- 逻辑宽
IMG.H = 300            -- 逻辑高
IMG.STD = 3.0          -- 使用的容差
IMG.ENC = "b64"        -- 块数据编码："b64" | "hex"
IMG.NBLK = 30612       -- 块数 = 需要的控件数
IMG.MAE = 1.17         -- 矩形合并的平均绝对色差（0~255/通道）
IMG.DATA = "..."       -- 编码后的块数据（一个字符串）
-- 注意：默认【不含】return 语句（见 4.1 的 WITH_RETURN 说明）
```

**字段说明**：

| 字段 | 类型 | 含义 |
|---|---|---|
| `N` | int | 边长（源像素，正方形） |
| `W` / `H` | int | 逻辑宽高（当前等于 N） |
| `STD` | number | 使用的容差（0~1024） |
| `ENC` | string | `"b64"`（7 字符/块）或 `"hex"`（10 字符/块） |
| `NBLK` | int | 块数 = **需要的控件数** |
| `MAE` | number | 矩形合并的平均绝对色差（0~255/通道，0 = 无损） |
| `DATA` | string | 编码后的块数据 |

#### 块数据位布局（★ 坐标 x,y 不存储）

块按**行主序扫描顺序**排列。第 i 块的 `x,y` 由解码端**重放扫描**还原：

```
维护 occupied[col] = 该列已被占用到的最大行号（初始 -1）
游标 (ci,cj) 从 (0,0) 起：
  跳过 occupied[ci] >= cj 的列；ci 越界则 cj += 1, ci = 0 继续跳
  → (x,y) = (ci,cj)
放块 (w,h) 后：occupied[ci .. ci+w-1] = max(旧值, cj+h-1) ； ci += w
```
> 该性质由 `compress.py` **自动自检**（`check_scan_order`，必须 0 处不一致），
> 因为"块列表必须是扫描顺序"是编码正确性的前提。

**hex 编码**（10 字符/块）：
```
w(2字符) h(2) r(2) g(2) b(2)      ← 每个字段 1 字节的十六进制
```

**b64 编码**（7 字符/块）：
```
组1（4 字符）：3 字节 w,h,r → 24 位 → 4×6 位
    a = ((c1*64+c2)*64+c3)*64+c4          < 2^24
    w = a // 65536 ; h = (a//256) % 256 ; r = a % 256
组2（3 字符）：2 字节 g,b → 16 位 → 3×6 位
    b2 = (c5*64+c6)*64+c7                 < 2^18
    g = b2 // 256 ; b = b2 % 256
```
字符表：标准 base64 `A-Za-z0-9+/`（**不含 `=` 填充**）。
颜色 = `r*65536 + g*256 + b`。

> ⚠️ **不要在 Lua 里把 5 字节合成一个 40 位大整数** —— 那需要 42 位中间值，
> 在 32 位整数实现下会回绕（实测：`807136431*64+24` 得到 `117124056`
> 而非 `51656731608`）。必须保证每步运算 < 2^24。

**不变式（本工具保证，且自动自检）**：
- 所有块互不重叠，且**完整覆盖**整个 `N×N` 区域（空洞 / 重叠 / 越界 必须全为 0）
- 所有块的边界都在整数像素坐标上 → 渲染时不会有缝隙
- 块色 = 该区域内像素的三通道均值（四舍五入）
- 块列表严格按扫描顺序 → 坐标可省略

### 6.5 `render.lua` 的可调参数

在 `RENDER` 表里：

| 参数 | 含义 | 建议 |
|---|---|---|
| `TEMPLATE` | 图片控件模板索引；0 = 自动探测 | 0 或填实际索引 |
| `TEMPLATE_SCAN` | 自动探测区间 | 一般不用改 |
| `UNIT` | 每个源像素占多少画布单位 | `"AUTO"`（按画布自适应，推荐）；也可填固定数字 |
| `MAX_RATIO` | 图最多占画布短边的比例 | `0.98` |
| `MARGIN_PX` | ★ 每块向外扩多少**源像素**（防细缝） | `0.20`；有细缝调到 0.35 / 0.50 |
| `MARGIN` | 旧口径：固定画布单位（绝对值） | `nil`（不填）。**高分辨率下会过度外扩 → 毛边** |
| `GROUPS` | ★ 显示分组数：建完每帧显示一组 | `16`。把"变可见"的成本摊到 K 帧 |
| `BUDGET` | ★ 分帧建立每帧预算（秒） | `0.040`（40 ms 平滑）；`0` = 不分帧 |
| `BUDGET_CHECK` | 每这么多个块查一次时钟 | `32`（`os.clock` 本身有成本） |

> ★ **`render.lua` 的建立方式：隐藏分组建立 → 建完分帧显示**
> （文档 §8.5 反复强调的做法，V1.1 起已在 `render.lua` 里实现）：
> - 控件挂在**隐藏的全屏透明组**下建立 → 稳态每帧开销约 **1.7 µs/个**，而不是可见态的 15~18 µs/个。
>   实测（§8.5）20,000 个控件：可见 301 ms/帧(3 fps) → 隐藏建立再显示 35 ms/帧，**约 9 倍**。
> - **建立本身**也分帧（`BUDGET`），所以不受"单次回调约 20 s"的看门狗约束，块数可以很大。
> - **"变可见"这个动作**同样分帧（`GROUPS` 组，每帧一组），避免一帧内重建全部渲染批次。
> - 隐藏/显示**必须用冒号调用**：`c:SetVisible(false)` ✓ ／ `c.visible = false` ✗（静默失败）。
>   脚本会把 `pcall` 的返回值打进日志（`分组隐藏 API：SetVisible=true SetActive=true`），
>   若为 false 会报错提示。
> - 分组创建失败时会**自动回退**为「直接挂在 host 下、全程可见」（画面正常但帧率差约 9 倍），并打警告。

**UNIT 怎么算**（`render.lua` 内部实现，与文档旧版不同，以代码为准）：

```
limit = math.min(canvasW, canvasH) × MAX_RATIO     -- 用【短边】，不是画布高
unit  = limit / math.max(IMG.W, IMG.H)             -- V1.1 起按两轴最大值
```
例（画布 1599×899，输出 300×300）：`limit = 899×0.98 = 881`，`unit = 881/300 ≈ 2.94`。

`render.lua` 已内置这个计算与越界自动缩小，所以填 `"AUTO"` 或填一个大致值都行。

## 9. 算法原理

### 9.1 最大对齐矩形合并

```
按行主序扫描每个未占用的像素 (i, j)：
  ① 向右扩宽 w：要求当前行 [i, i+w) 内三通道极差 ≤ STD
  ② 向下扩高 h：要求整个 w×h 矩形内三通道标准差 ≤ STD
  ③ 在所有可行 (w, h) 中取【面积最大】者作为一块
  ④ 标记该区域已占用，块色 = 区域均值
  ⑤ 继续扫描
```

### 9.2 三个设计选择及原因

| 选择 | 原因 |
|---|---|
| **判据用标准差**（而非"与基准像素比较"） | 抗离群像素。早期版本用"向左上角像素比较"，一个离群点就把大片平涂区域切碎（实测表现为圆形装饰断裂、边缘碎裂） |
| **代表色用区域均值** | 让整块的视觉偏差最小，而非偏向某一个像素 |
| **矩形边界必须整数像素** | 否则相邻块出现发丝缝 |

### 9.3 加速：积分图

预计算每通道的"和"与"平方和"积分图（summed-area table），
使**任意矩形的均值与方差都是 O(1)**（4 次查表）。300×300 压缩约 1 秒。

### 9.4 与其他方案的实测对比（300×300，STD=3）

| 算法 | 块数 | 说明 |
|---|---|---|
| 水平 RLE | 最多 | 只能利用行内 + 垂直同色，太保守 |
| 四叉树（2^k 递归） | 33,151 | 边界天然对齐，但受 2 的幂网格限制 |
| **最大对齐矩形（本工具）** | **30,612** | 不受 2 的幂限制，比四叉树多压 8% |
| 贪心只向右下扩（早期版本） | 38,027 | 离群像素会导致碎裂，已弃用 |

### 9.5 为什么不做"降色数压缩"

实测：把 300×300 插画量化到 4 位/通道（16 级 = 4096 色）后，
块数**反而从 30,612 升到 37,662**，且 MAE 从 1.17 升至 3.49。
**量化是纯失真来源，不是压缩来源。**

## 10. 故障排查

| 症状 | 原因 | 解决 |
|---|---|---|
| **完全没有日志、没有画面** | 脚本语法错误（Lua 在编译期就失败，整个 chunk 不执行）。最常见原因：**把带 `return` 的输出粘进了 render.lua** | 跑 `python selftest.py`；或 `node check_lua.js 你的文件.lua`。输出不要带 `return`（见 4.1） |
| 卡死 / 反复重建 | 控件数超上限 | 提高 STD 或降低分辨率，使块数 ≤ 45,000（实测 50,000 正常、61,440 崩溃） |
| 找不到模板 | 关卡里没有"已存为客户端模板"的图片控件 | 按 6.1 创建模板；或把 `RENDER.TEMPLATE` 填成实际索引 |
| 画面有发丝缝 | 外扩量太小 | 调大 `RENDER.MARGIN_PX`（0.20 → 0.35 → 0.50） |
| **画面有规律毛边/锯齿** | `MARGIN` 用了固定画布单位（旧口径） | 改用 `MARGIN_PX`；见 6.5 |
| 图超出画布 / 被裁切 | `UNIT` 太大 | 用 `"AUTO"`，或减小 `UNIT`（render.lua 也会自动缩小并打日志） |
| 画面糊 / 有块状感 | STD 太大 | 降低 STD（代价是控件数上升） |
| 边缘有彩色毛边 | 12 位量化 + 容差合并叠加 | 保持 `COLOR_BITS = 8`（不量化） |

### 11.1 最小调用链

```bash
# 1) 估控件数（快速，选参数）
python estimate.py --input IMG --size WxH --scan-std

# 2) 压缩（选定 STD 后）
python compress.py --input IMG --output OUT.lua --std S --size WxH

# 3) 把 OUT.lua 的内容替换进 render.lua 的【数据区】，再部署
```

### 11.2 程序化调用（不经命令行）

`compress.py` 与 `estimate.py` 的核心函数可直接 import：

```python
import sys
sys.path.insert(0, "最大对齐矩阵合并压缩")

from compress import load_and_prepare, quantize, pack_rects, write_lua
from estimate import count_blocks

arr = load_and_prepare("a.png", 300, 300, lock_aspect=False)
q = quantize(arr, 8)
blocks = pack_rects(q, 3)          # → [(x,y,w,h,color), ...]
write_lua("out.lua", blocks, 300, 300, 3, 8, "b64", mae, var_name="IMG")
#           └ path  └ blocks └ W └ H └ std └ bits └ enc └ mae   ← enc / mae 是必填！

n, avg = count_blocks(q, 3)        # 只要块数
```

### 11.3 拼接 render.lua 的确定性做法

`render.lua` 的数据区用固定标记包围，可程序化替换：

```
起始标记:  local IMG = {}
结束标记:  -- ▲▲▲ 数据区结束 ▲▲▲
```

即：把从 `local IMG = {}` 到 `-- ▲▲▲ 数据区结束 ▲▲▲` 之前的那几行，
整段替换为 `compress.py` 输出文件的内容。

### 11.4 不做的事（已实测排除，别浪费时间）

| 想法 | 结论 |
|---|---|
| 降低颜色位数以减少控件 | ❌ 块数反而增加，且引入可见失真 |
| 少设属性以加快建立 | ❌ 无收益（首写属性后其余极便宜） |
| 用"多控件模板"一次建出多个控件 | ❌ 引擎不支持（只能引用单个控件模板） |
| 用容器/服务器模板打包 | ❌ 服务器模板是 3D 元件，产不出 UI 控件 |
| 时间复用（1 控件当 N 用） | ❌ 每帧需重写全部控件（0.012 ms/次），CPU 线性爆炸 |
| **分块挂载（多父节点）加速建立** | ❌ **实测退化曲线完全不变**（16.8 万控件分 12 组也一样） |
| **加大每帧批量加速建立** | ❌ **只快约 1.4 倍**（主导项是引擎内部的 N² 项，与批量无关） |
| **控件复制（Clone/Copy/Duplicate）** | ❌ **9 种 API 全部不存在** |
| **用 `c.visible = false` 隐藏** | ❌ **点号赋值静默失败**；必须 `c:SetVisible(false)` |

### 11.5 边界数值速查

| 项 | 值 |
|---|---|
| **单次回调时长上限** | **约 20 s**（超时 → `Lua execution took too long` 并**静默中断**脚本）|
| 单次回调建完的安全控件数 | **45,000 ~ 50,000** |
| 控件数**硬上限** | **没有**（实测 100,000 稳定；需分帧创建）|
| 建立耗时模型 | `T(ms) = 0.27·N + 3.75e-6·N²` |
| 每帧渲染成本 | **15~18 µs × 可见控件数**（5,000→12 fps，20,000→3 fps）|
| 每帧渲染成本（隐藏态） | **约 1.7 µs × 控件数**（隐藏建立 → 显示 后仍约 1.8 µs ✓）|
| 建议每帧建立预算（分帧） | **40 ms**（平滑；加大只快 1.4 倍）|
| 动态 STD 收益 | 块数 **−30~34%**（细节区画质持平）|
| 块数据编码 | `b64` 7 字符/块（默认）/ `hex` 10 字符/块 |
| 编码运算约束 | 每步 < 2^24（不能假设 64 位整数） |
| 每控件建立耗时 | **0.27 ms**（N 小时）；N=20,000 时约 0.40 ms |
| 每控件属性写入 | **0.012 ms** |
| 引擎内置纯色图片 ID | `100001` |
| 示例设备画布 | `1599 × 899` 画布单位 |
| 画布单位 → 物理像素 | ×1.707（随设备变化） |
